## Pinned sources and Runner v13.2.0 behavior

The exact GitHub tags were checked: [`actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1`](https://github.com/actions/checkout/tree/3d3c42e5aac5ba805825da76410c181273ba90b1) is v7.0.1; [`actions/setup-node@820762786026740c76f36085b0efc47a31fe5020`](https://github.com/actions/setup-node/tree/820762786026740c76f36085b0efc47a31fe5020) is v7.0.0. Both SHA tags also resolve identically in the Forgejo `data.forgejo.org/actions/` mirrors at research time. Check the actual Forgejo task's `default_actions_url` (Runner [`internal/app/run/runner.go`](https://code.forgejo.org/forgejo/runner/src/tag/v13.2.0/internal/app/run/runner.go)): shorthand `actions/name@sha` resolves against this configured/default URL. If it points elsewhere, use explicit pinned `https://github.com/actions/name@sha` URLs; Runner's [`newRemoteAction`](https://code.forgejo.org/forgejo/runner/src/tag/v13.2.0/act/runner/step_action_remote.go) supports that syntax. Do not replace a pinned SHA with an unverified tag.

- **Fetch / checkout:** Runner v13.2.0 [`stepActionRemote.prepareActionExecutor`](https://code.forgejo.org/forgejo/runner/src/tag/v13.2.0/act/runner/step_action_remote.go) performs a Git clone of Action source into its **own host-side action worktree/cache**, then parses `action.yml`. This is not the target repository checkout. For normal Forgejo jobs [`NoSkipCheckout: true`](https://code.forgejo.org/forgejo/runner/src/tag/v13.2.0/internal/app/run/runner.go), so `actions/checkout` is **not** skipped. The Action's bundled `dist/index.js` does the target-repository checkout inside the **job Pod**; it needs Node, Git >= 2.18, Forgejo repo reachability and the normal job token while fetching. `persist-credentials: false` means the Action must not leave credentials in Git config after checkout; its JS post handler can run at job teardown. The plugin does not fetch either repository directly or implement Git.
- **CopyIn / entrypoints:** [`runActionImpl` and `maybeCopyToActionDir`](https://code.forgejo.org/forgejo/runner/src/tag/v13.2.0/act/runner/action.go) call Runner `CopyDir` for remote JS Action files, which the plugin adapter tar-streams to `CopyIn` under `/shared/act/actions/…`. The plugin's Kubernetes `pods/exec` invokes GNU `tar` *inside the job image* to unpack files, then Runner requests `Exec(["node", "/shared/act/actions/…/dist/…js"], env, …)` for the main Action. `checkout` v7.0.1 and `setup-node` v7.0.0 both declare **`runs.using: node24`**, but Runner does **not** supply or stage a Node 24 executable: it runs `node` from the environment PATH. Runner also runs any declared JS pre/post scripts with `node`. Docker/container Actions remain unsupported, but these two are JavaScript Actions, not Docker Actions.
- **Runtime prerequisite, not a substitute for Actions:** the existing `ubuntu:24.04` job image has no Node executable. The first test must explicitly coordinate the configured `JOB_IMAGE` and matching Runner label to an **ordinary multiarch image with Node 24 bootstrap runtime, Git, bash/sh, GNU tar, env, CA certificates and writable nonroot workspace** (for example evaluate the official `node:24-bookworm` image; verify actual ARM64 manifest and tools first). This is a bootstrap interpreter, **not** a replacement for `actions/setup-node`: the Action still reads `.node-version`, obtains/selects the requested project Node version, writes `$GITHUB_PATH`, and is validated by the later shell step checking the toolcache-selected `node`. Do not quietly use a custom prebuilt CI image or alter the pinned Actions. Changing the job image is deployment/Runner-label configuration, not a plugin feature, and requires the cluster agent's explicit choice. For example, *if the official image is validated*, keep `runs-on: k3s` but configure `JOB_IMAGE=node:24-bookworm` **and** `runner.labels: ['k3s:kubernetes://node:24-bookworm']` together; for a digest-pinned image both values must exactly match the chosen reference. The example is a proposed runtime prerequisite, not a claim that this image passed k3s. Keep the job Pod without Kubernetes credentials and keep job→plugin gRPC blocked.
- **Step files and propagation:** [`runStepExecutor`](https://code.forgejo.org/forgejo/runner/src/tag/v13.2.0/act/runner/step.go) stages empty `workflow/{envs.txt,outputcmd.txt,pathcmd.txt,statecmd.txt,SUMMARY.md}` via `CopyIn` and sets both `GITHUB_*` and `FORGEJO_*` paths. After each pre/main/post stage it invokes `CopyOut` for env, state, output, summary and path. Runner parses env/output/state itself ([`ParseEnvFile`](https://code.forgejo.org/forgejo/runner/src/tag/v13.2.0/act/container/parse_env_file.go)) and merges env into later steps (`rc.Env`/`GlobalEnv`); [`UpdateExtraPath`](https://code.forgejo.org/forgejo/runner/src/tag/v13.2.0/act/runner/run_context.go) reads GITHUB_PATH and prepends paths to later Exec environments. State is supplied as `STATE_*` to post scripts; outputs/summary are Runner responsibilities. Existing `CopyIn`/`CopyOut` and shared `emptyDir` can transport these files in principle; the shell-only integration already exercised file-command CopyOut, **not** Action-specific contents. `setup-node`'s `package-manager-cache: false` disables npm package-manager caching; its versioned Node tool cache still uses `/shared/toolcache` and `/shared/tmp` (ephemeral per Pod).

## Confirmed alpha.2 failure and environment contract

The pinned workflow on v0.1.0-alpha.2 fetched both Actions from `data.forgejo.org` at the expected SHAs, then checkout `Exec` failed with `InvalidArgument: invalid environment variable` (and its post step failed). Runner [`Step.GetEnv`](https://code.forgejo.org/forgejo/runner/src/tag/v13.2.0/act/model/workflow.go) generates `INPUT_FETCH-DEPTH`, `INPUT_PERSIST-CREDENTIALS`, `INPUT_NODE-VERSION-FILE`, `INPUT_PACKAGE-MANAGER-CACHE`, etc.; the alpha.2 plugin rejected these because it required shell-identifier keys (`[A-Za-z_][A-Za-z0-9_]*`).

`plugin.v1alpha` defines Exec env as an unrestricted `map<string,string>`; Runner passes these keys without normalizing them. Kubernetes [`PodExecOptions.Command`](https://pkg.go.dev/k8s.io/api/core/v1#PodExecOptions) is an argv list, **not** an environment declaration. The plugin invokes `/usr/bin/env -i -- PATH=… /bin/sh -c '… cd …; exec /usr/bin/env -i -- "$@"' forgejo WORKDIR PATH=… KEY=value … COMMAND`. Kubernetes exec transports this as argv. The shell receives only a safe PATH; Action assignments remain positional arguments until **after** the cwd shell exits: some `/bin/sh` implementations discard non-identifier environment keys on startup (caught by release CI). Neither keys nor values are interpolated into shell source. GNU `env` and Linux `execve` transport hyphens, dots and other non-identifier characters. `--` ends env's option parsing before assignments (including a key beginning with `-`). The corrected rule rejects empty names (not reliably usable through shells), names containing `=` (ambiguous assignment separator), and NUL in names **or values** (cannot be an argv/envp string). Values containing `=` are valid. This is the only plugin change for the observed failure. **Rerun the exact pinned workflow with the new image digest before claiming the Actions execute successfully.**

The initial shell image (`JOB_IMAGE=ubuntu:24.04`, label `k3s:kubernetes://ubuntu:24.04`) cannot bootstrap a `node24` Action; coordinate an appropriate job image separately if this has not already been done.

## Alpha.3 checkout failure: HOME, not a missing Git checkout

The real alpha.3 run reached checkout Main in `/workspace/scojo/pi-wright` with Git 2.39.5, then printed `Removing auth` and `fatal: --local can only be used inside a git repository`. This is **not** evidence that Runner should pre-populate `.git`: on a fresh job the directory should exist and be empty. Runner v13.2.0 computes `/<container.workdir_parent>/<owner>/<repo>` as the workdir, mounts an empty Docker volume *at that path*, and sets `GITHUB_WORKSPACE` and `FORGEJO_WORKSPACE` to the same path. The plugin adapter sends the Runner working directory as `ExecRequest.workdir`, even when its caller omits an explicit override. The plugin mounts one emptyDir at both `/workspace` and `/shared`, then `mkdir -p` and `cd` to the exact requested cwd before executing Node. Pod startup creates `act`, `tmp`, `toolcache`, `workdir` under `/shared` (therefore also visible under `/workspace`); `/workspace/scojo` and `/workspace/scojo/pi-wright` are created by the first workdir Exec if not already present. No code initializes `.git` in any of these paths. The mount boundary is `/workspace` instead of Docker's mount at the repository workdir, but both start without a repository; Git's mount-boundary diagnostic is a consequence of probing before `git init`, not an instruction to cross mounts. The Action creates the Git repository itself *after* setting up its temporary global config.

**Classification: plugin defect (Exec environment), not workspace initialization, protocol insufficiency, or Forgejo Action incompatibility.** Docker/Podman Exec inherits the container environment and its usual HOME; the plugin's `env -i` discarded it, and returned only PATH as image env. The protocol permits the plugin to provide a usable HOME. Checkout v7.0.1's default `set-safe-directory: true` runs `git-auth-helper.configureTempGlobalConfig()` immediately after the version check. It calls Node `os.homedir()` if `HOME` is unset. The plugin previously ran every Exec with `env -i`, passing Runner's env but no default `HOME`; the job's fixed numeric UID 10001 has no passwd entry. Local reproduction with the exact pinned checkout `dist/index.js`, the matching Node 24/Git 2.39.5 image and an empty writable `/workspace` produced the **same** `Removing auth`/`git config --local`/`submodule foreach`/exit 128 sequence. Running the same reproduction with only `HOME=/shared/workdir` added proceeded through `Temporarily overriding HOME`, `Deleting the contents`, `git init` and `Setting up auth` before reaching the expected network-disabled fetch failure. This isolates the plugin's missing usable HOME rather than a missing pre-initialized repo; the real Pod's pre-checkout contents were **not** captured in the logs.

The first exception is masked: `git-source-provider.getSource()` executes `authHelper.removeAuth()` in a `finally` even before `git init`, if `persist-credentials: false`. `removeGitConfig()` tolerates `git config --local` exit 128 while probing for a key, but unconditional `removeSubmoduleGitConfig()` invokes `git submodule foreach` without a repository and throws; that secondary error is what Runner reports. Checkout Post checks whether `.git/config` exists and exits successfully when absent. The plugin correction is restricted to setting a default `HOME=/shared/workdir` for Exec when Runner did not explicitly supply HOME. The directory already exists, is writable on the shared emptyDir, and is outside the target repository; no Git initialization, mount change or special checkout behavior is added. Rerun the **unchanged pinned workflow** against the new digest; the local reproduction does not prove real ARM64 checkout/setup-node succeeds. If a later failure genuinely depends on the *actual* Pod contents before Main (not just this source-derived layout), capture a read-only `stat -c '%d %u:%g %a %n' /workspace /workspace/scojo /workspace/scojo/pi-wright`, `test -e /workspace/scojo/pi-wright/.git`, and `printf 'HOME=%s GITHUB_WORKSPACE=%s\n' "$HOME" "$GITHUB_WORKSPACE"` immediately before checkout. Do not print tokens or change the pinned Actions to diagnose it.

Other conditions to check *only if observed*: job Pod egress to its Forgejo Git endpoint and to the chosen Node distribution source (and Runner egress to the pinned Action source); writable `/shared/toolcache`, `/shared/tmp`, `/workspace`; enough ephemeral storage for Action source and the selected Node version. No per-job Service/PVC/SA is required by this test. Do not relax the enforced Runner→plugin-only ingress policy to solve downloads.

**Success gate:** evidence that both pinned `uses:` Actions actually executed (including checkout and setup-node logs, not just successful shell commands); target repo files and commit visible from the Pod; project Node selected in `/shared/toolcache`, `npm` usable; post-step and post-job file commands complete; Pod removed; job Pod has no Kubernetes credentials and cannot reach plugin gRPC. On failure record the exact RPC/step, exit/error, Pod status/events and which network connection was denied. Stop after this small slice; do not port install/build/test/publish jobs without reassessment.
