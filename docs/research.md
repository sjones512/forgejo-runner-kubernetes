## Protocol and minimal mapping

Runner connects to a standalone gRPC server with `plugin.v1alpha.BackendPlugin` and standard `grpc.health.v1`. Configure `plugins.kubernetes.address`, then `runner.labels: ['k3s:kubernetes://ubuntu:24.04']`, with `runs-on: k3s` (label image is overridable by `jobs.<id>.container.image`). Runner owns workflow parsing and sends `Capabilities` once, then `Create` -> `Start` -> repeated `CopyIn` / `Exec` / `CopyOut` -> `Remove`. **All seven RPCs matter even for a shell `run:`**: Runner uploads the script with CopyIn and reads per-step env/output files with CopyOut. `Create` returns path layout and OS/arch. In the example label `k3s:kubernetes://ubuntu:24.04`, **Runner v13.2.0 sends `label_arg: ubuntu:24.04` but `image: ""` for a job without `container:`** (`startPluginEnvironment` calls `containerImage()`, which returns empty for absent `job.Container()`). The release announcement suggests the label value is sent as `image`, but that does not match this source path. This plugin requires the suffix to match the configured image for a plain job, and rejects an alternate `container.image` override. `Start` must send `StartComplete`; `Exec` streams separate stdout/stderr and finishes with `ExecComplete(exit_code)` for command exits versus `ExecFailed` for infrastructure errors. Empty/missing env files must be tolerated. `Remove` deletes the Pod. Runner cancels streams on timeout/cancel and may call Remove before cancellation handlers finish. `CopyIn` first frame must contain ID and destination; subsequent frames must contain neither.

Proposed slice: `Create` creates one Pod in a fixed namespace; deterministic name derived from Runner's per-job name (hash; Runner's name includes a task ID), labels identify ownership. `Start` waits for Running/ready, detects image pulls/scheduling failure, returns terminal completion. `Exec` uses Kubernetes `pods/exec` remotecommand **without TTY** for independent stdout/stderr and Kubernetes exit status. `CopyIn`/`CopyOut` use streaming tar via `pods/exec` (not kubectl). `Remove` deletes Pod idempotently. CLI uses in-cluster `rest.InClusterConfig`, no kubeconfig. Health service indicates plugin readiness, not individual Pod health.

**Image/workspace tradeoff:** Kubernetes exec has no per-command environment, user or working-directory override. v0.1 deliberately supports only the tested multiarch `ubuntu:24.04` job image, with `/bin/sh`, `env`, `mkdir`, `tar` available; exec wraps argv to set env and workdir. Files live in one `emptyDir` mounted at `/shared` and `/workspace` (Runner's default `container.workdir_parent` is `workspace`, and its job workdir is `/workspace/<repo>`); the returned temp path is `/shared/tmp`. Non-default `workdir_parent` is unsupported. A helper container with a bespoke file-transfer/exec agent would allow arbitrary minimal job images but would substantially increase the privilege, image-build and process-control surface; defer until a real workflow requires it. No arbitrary job images or `user` override in this slice. Tar-stream transport preserves Runner's archive semantics; no `kubectl cp` or local tar subprocess. Validate paths, reject unsupported service containers/backend options and capability escalation rather than silently changing behavior.

Pod: restart Never, ARM64 node selector initially (configurable only after proof if necessary); bounded CPU/memory/ephemeral storage; no ServiceAccount token, privilege escalation or Linux capabilities, RuntimeDefault seccomp, ephemeral emptyDir. Plugin ServiceAccount Role in fixed job namespace: `pods` create/get/delete (optionally list for later orphan sweep); `pods/exec` create. No cluster-admin. RBAC cannot restrict pod contents: compromised plugin credentials could still create malicious Pods. **Critical protocol trust boundary:** Runner v13.2 connects over unauthenticated plaintext gRPC. An untrusted job able to reach the plugin Service can invoke its privileged RPCs. For separate plugin/Runner Pods, deploy the plugin in a **different namespace from the job Pods**, bind its ServiceAccount to the job namespace Role, and enforce ingress NetworkPolicy allowing only trusted Runner Pods (see `deploy/plugin-network-policy.yaml`; requires CNI enforcement), or co-locate them behind a private UNIX socket. Separate plugin and job SA identities alone are NOT sufficient. Jobs can reach other networks by default unless cluster admin also applies egress policy. Set quota/LimitRange/egress policies externally.

Risks / non-goals: alpha proto may change; exec transport cancellation is not a strong remote process-kill guarantee (delete Pod on cancellation, Runner Remove follows); no generic image ENV introspection, user switching, image selection, service containers, container actions, persistent cache, orphan sweeper, cross-RPC restart recovery. Startup image-pull errors, API failures and cleanup need bounded timeouts. Deterministic ID + ownership label permit a future orphan audit; a plugin crash after Pod creation can leak a Pod until manually removed. Real workflow must be tested on ARM64 k3s before claiming M7.

Sequence: (M0) pin proto, note limits; (M1) gRPC + health; (M2) Pod spec and create; (M3-M5) upload script, exec, stream outputs and exits, read env files; (M6) cleanup/cancellation; (M7) real Runner workflow in disposable kind then ARM64 k3s. **Stop after M7** to evaluate protocol fit, security compromises, cleanup and remaining useful-workflow gaps.
