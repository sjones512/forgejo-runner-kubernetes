# Vitest fork termination: containerd AppArmor signal denial

**Status:** The real ARM64 `pi-wright` verify job passed checkout, setup-node, pnpm install, generated checks, typecheck, and build. Vitest ran tests but failed repeatedly on `ChildProcess.kill()` of fork workers with **`EACCES` (errno 13)**. Runner correctly reported exit 1. Separate cluster testing subsequently reproduced the signal denial with both Node and shell through Runner → plugin → Kubernetes `pods/exec`, and correlated it with AppArmor node audit records. The full verify job has **not** yet passed, nor has an AppArmor override been tested there.

## What the plugin actually does

`internal/plugin/server.go` creates one job container with `runAsNonRoot: true`, `runAsUser: 10001`, `fsGroup: 10001`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, Pod `seccompProfile: RuntimeDefault`, and (by default) **no explicit AppArmor profile**. The optional `JOB_APPARMOR_PROFILE` override, when set, affects only the job container's AppArmor field. The container init runs `sh -c 'mkdir … && exec sleep infinity'`. `internal/plugin/transport.go` uses `PodExecOptions{Container: "job", Command: argv, TTY: false}` through the Kubernetes API and `client-go/remotecommand.NewSPDYExecutor`; it does **not** set an exec UID, call `setuid`, alter capabilities, or run workers itself. The cwd/env wrapper uses `/bin/sh` and `/usr/bin/env`, then `exec`s the requested command. The executable (`pnpm`/Node) forks its own workers. Kubernetes forwards the exec request through kubelet's CRI to the container runtime; the plugin does not spawn those processes on its host.

Read-only Kubernetes inventory showed node-1/2/3 on **Ubuntu 26.04.1, kernel 7.0.0-1019-raspi, containerd 2.3.4-k3s1**. In the cluster's reproduced failure, the container init had AppArmor label `cri-containerd.apparmor.d`, while the `pods/exec` process and its child had `cri-containerd.apparmor.d//&unconfined`. The Node child-spawn succeeded, but `ChildProcess.kill('SIGTERM')` failed with `EACCES` / syscall `kill`; a shell child-kill also received `Permission denied`. Node audit records for both failures showed `apparmor="DENIED" operation="signal" profile="cri-containerd.apparmor.d" requested_mask="send" denied_mask="send" signal=term peer="cri-containerd.apparmor.d//&unconfined"`.

## Minimal reproduction through Runner → plugin

Copy the dependency-free [Node signal probe](../examples/exec-signal-probe.cjs) into an isolated diagnostic job and execute it **as a normal `run:` step on the same plugin runner label and job image** (not as a process on the Runner host). It prints *only* relevant `/proc/1`, parent and child credential/namespace/security fields; it forks a child, calls `ChildProcess.kill('SIGTERM')`, waits for exit, and has a 5-second self-terminating child if the signal is refused. Do not run this in another workflow's active job Pod. A shorter complementary shell probe, likewise as a plugin `run:` step:

```sh
sh -c 'sleep 5 & child=$!; kill -TERM "$child"; sent=$?; wait "$child"; waited=$?; printf "kill=%s wait=%s\n" "$sent" "$waited"; test "$sent" -eq 0 && test "$waited" -eq 143'
```

The original development-host baseline (UID 1000, no effective capabilities, seccomp 0) passed Node and shell signaling. It was not a substitute for the subsequently confirmed in-Pod failure. Keep the minimal probes available for validating any runtime fix or explicit cluster override before rerunning the full workflow.

For a failed *in-Pod* probe, retain the three `Uid`/`Gid` four-tuples, `Groups`, `CapEff`/`CapBnd`, `NoNewPrivs`, `Seccomp` and `Seccomp_filters`, `NSpid`, `PPid`, `ns/{pid,user}`, `{uid,gid}_map`, and `/proc/{1,parent,child}/attr/{current,apparmor/current}` (where readable). From the node hosting that job, have the cluster operator inspect kernel/audit logs for **`apparmor="DENIED" operation="signal"`**, including `profile`, `peer`, `requested_mask`, `denied_mask` and `signal`. A narrow `strace -f -e trace=kill,pidfd_send_signal` can differentiate syscalls if ptrace is permitted; it is not required to run the reproduction. Do not collect job tokens or print full process environments.

## Diagnosis and operator decision

[Linux `kill(2)`](https://man7.org/linux/man-pages/man2/kill.2.html) allows signaling when sender's real/effective UID equals target's real/saved-set UID, or with `CAP_KILL` in the target user namespace; ordinary DAC denial is **`EPERM`**, not `EACCES`. A fork should inherit credentials, namespaces, seccomp and the AppArmor label unless something explicitly transitions. Matching UIDs are therefore not enough if an LSM separately denies `signal`; seccomp can also return an explicitly configured errno. `EACCES` is a clue, **not** proof of a particular policy or of differing UIDs.

[containerd issue #12886](https://github.com/containerd/containerd/issues/12886) describes a notably similar CRI-exec problem on **k3s, Ubuntu 26.04 and containerd 2.3.1**: exec-created processes can receive a stacked AppArmor label such as `cri-containerd.apparmor.d//&unconfined`, whereas PID 1 has `cri-containerd.apparmor.d`. The [containerd v2.3.4 AppArmor template](https://github.com/containerd/containerd/blob/v2.3.4/contrib/apparmor/template.go) permits `signal (send,receive) peer={{.Name}}` but not the stacked peer. The upstream report demonstrates that even a simple `kubectl exec … sh -c 'sleep … & kill $!'` can fail; see the proposed [containerd fix #12887](https://github.com/containerd/containerd/pull/12887) for the upstream change. The cluster's label and audit evidence confirms the same class of AppArmor signal denial. An `EACCES` from an LSM can occur despite matching UID and absent capabilities; `CAP_KILL` addresses the DAC exception, not an AppArmor peer-label mismatch.

Classify this as a **Kubernetes/container-runtime AppArmor-profile limitation**, not a plugin Exec defect. A runtime fix or node profile change belongs to cluster maintainers. This plugin now offers an optional, **unset by default**, job-container AppArmor override: the affected homelab has explicitly accepted `JOB_APPARMOR_PROFILE=unconfined` as a temporary loss of AppArmor confinement while keeping seccomp RuntimeDefault and the remaining Pod security controls. This override has **not** yet been integration-verified. Remove it when the runtime no longer exhibits the issue. See [cluster-integration.md](cluster-integration.md#job-apparmor) for the security tradeoff and settings.
