# Vitest fork termination: diagnostic handoff (no plugin change)

**Status:** The real ARM64 `pi-wright` verify job passed checkout, setup-node, pnpm install, generated checks, typecheck, and build. Vitest ran tests but failed repeatedly on `ChildProcess.kill()` of fork workers with **`EACCES` (errno 13)**. Runner correctly reported exit 1. This is a process-signaling investigation, not evidence to add `CAP_KILL` or to disable confinement. **No minimal signal test has yet been run in the job Pod or through the plugin's real Kubernetes Exec path.**

## What the plugin actually does

`internal/plugin/server.go` creates one job container with `runAsNonRoot: true`, `runAsUser: 10001`, `fsGroup: 10001`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, Pod `seccompProfile: RuntimeDefault`, and **no explicit AppArmor profile**. The container init runs `sh -c 'mkdir … && exec sleep infinity'`. `internal/plugin/transport.go` uses `PodExecOptions{Container: "job", Command: argv, TTY: false}` through the Kubernetes API and `client-go/remotecommand.NewSPDYExecutor`; it does **not** set an exec UID, call `setuid`, alter capabilities, or run workers itself. The cwd/env wrapper uses `/bin/sh` and `/usr/bin/env`, then `exec`s the requested command. The executable (`pnpm`/Node) forks its own workers. Kubernetes forwards the exec request through kubelet's CRI to the container runtime; the plugin does not spawn those processes on its host.

Read-only Kubernetes inventory during this investigation showed node-1/2/3 on **Ubuntu 26.04.1, kernel 7.0.0-1019-raspi, containerd 2.3.4-k3s1**; an existing job Pod was on node-1 with UID 10001 and RuntimeDefault seccomp, with no Pod AppArmor field. That inventory establishes neither the actual exec/child credentials nor the effective AppArmor label; do not infer them from Pod spec alone.

## Minimal reproduction to run in an isolated job via Runner → plugin

Copy the dependency-free [Node signal probe](../examples/exec-signal-probe.cjs) into an isolated diagnostic job and execute it **as a normal `run:` step on the same plugin runner label and job image** (not as a process on the Runner host). It prints *only* relevant `/proc/1`, parent and child credential/namespace/security fields; it forks a child, calls `ChildProcess.kill('SIGTERM')`, waits for exit, and has a 5-second self-terminating child if the signal is refused. Do not run this in another workflow's active job Pod. A shorter complementary shell probe, likewise as a plugin `run:` step:

```sh
sh -c 'sleep 5 & child=$!; kill -TERM "$child"; sent=$?; wait "$child"; waited=$?; printf "kill=%s wait=%s\n" "$sent" "$waited"; test "$sent" -eq 0 && test "$waited" -eq 143'
```

On this development host (UID 1000, no effective capabilities, seccomp 0), the probe's Node parent and child both had real/effective/saved UID and GID **1000**, and Node `ChildProcess.kill(SIGTERM)` returned true with `signal: SIGTERM`. The shell probe returned kill=0, wait=143. **Neither host test used the Kubernetes exec runtime and neither proves the ARM64 job's behavior.** Do not add a plugin fix or release based on those tests alone.

For a failed *in-Pod* probe, retain the three `Uid`/`Gid` four-tuples, `Groups`, `CapEff`/`CapBnd`, `NoNewPrivs`, `Seccomp` and `Seccomp_filters`, `NSpid`, `PPid`, `ns/{pid,user}`, `{uid,gid}_map`, and `/proc/{1,parent,child}/attr/{current,apparmor/current}` (where readable). From the node hosting that job, have the cluster operator inspect kernel/audit logs for **`apparmor="DENIED" operation="signal"`**, including `profile`, `peer`, `requested_mask`, `denied_mask` and `signal`. A narrow `strace -f -e trace=kill,pidfd_send_signal` can differentiate syscalls if ptrace is permitted; it is not required to run the reproduction. Do not collect job tokens or print full process environments.

## Working hypothesis, *not* an observed in-Pod diagnosis

[Linux `kill(2)`](https://man7.org/linux/man-pages/man2/kill.2.html) allows signaling when sender's real/effective UID equals target's real/saved-set UID, or with `CAP_KILL` in the target user namespace; ordinary DAC denial is **`EPERM`**, not `EACCES`. A fork should inherit credentials, namespaces, seccomp and the AppArmor label unless something explicitly transitions. Matching UIDs are therefore not enough if an LSM separately denies `signal`; seccomp can also return an explicitly configured errno. `EACCES` is a clue, **not** proof of a particular policy or of differing UIDs.

[containerd issue #12886](https://github.com/containerd/containerd/issues/12886) describes a notably similar CRI-exec problem on **k3s, Ubuntu 26.04 and containerd 2.3.1**: exec-created processes can receive a stacked AppArmor label such as `cri-containerd.apparmor.d//&unconfined`, whereas PID 1 has `cri-containerd.apparmor.d`. The [containerd v2.3.4 AppArmor template](https://github.com/containerd/containerd/blob/v2.3.4/contrib/apparmor/template.go) permits `signal (send,receive) peer={{.Name}}` but not the stacked peer. The upstream report demonstrates that even a simple `kubectl exec … sh -c 'sleep … & kill $!'` can fail; the proposed narrowly scoped [containerd fix #12887](https://github.com/containerd/containerd/pull/12887) is still under review. Our cluster's OS/runtime versions match the report, but **we have not inspected its AppArmor labels or audit records**. An `EACCES` from an LSM can occur despite matching UID and absent capabilities; `CAP_KILL` addresses the DAC exception, not an AppArmor peer-label mismatch.

**Decision gate:** If the in-Pod Node/shell parent cannot kill its same-UID child *and* AppArmor audit records show the stacked-peer signal denial, classify as **Kubernetes/container-runtime AppArmor-profile limitation**, not a plugin Exec/Pod UID defect or Vitest incompatibility. A node/operator-scoped profile fix or runtime update belongs to cluster maintainers. Setting the Pod to AppArmor `Unconfined` as a plugin shortcut would remove an established MAC confinement boundary; do **not** make that change without an explicit security decision. If the simple child test succeeds, inspect Vitest workers' actual credential/profile/namespace and target PID/PGID before assigning a cause. If simple signaling fails with a different audit/credential result, reassess seccomp and process credentials. **No plugin changes, added capabilities or new release until the real process and audit evidence justify one.**
