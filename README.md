# forgejo-runner-kubernetes (experimental)

Proof-of-concept **execution plugin**, not a new CI engine. Licensed under [MIT](LICENSE). Forgejo Runner handles workflows; this gRPC server uses its in-cluster Kubernetes identity to create one ephemeral Pod per job and forward file transfers, stdout/stderr and process exit status through Kubernetes `pods/exec`. **Experimental, not production-ready. Operator-supplied ARM64 integration evidence now covers JavaScript Actions, transfers, quiet Exec, per-job images, historical native image builds and registry publication. A passing full verification suite has not been demonstrated.**

Target: **Forgejo Runner v13.2.0** (`plugin.v1alpha`, commit `df6b843fb929bb04b933b09c6bf208774d42480b`). See [research / protocol mapping / tradeoffs](docs/research.md) and the [cluster integration contract](docs/cluster-integration.md). Protocol is alpha and may change without notice. Implemented RPCs: Capabilities, Create, Start, Exec, CopyIn, CopyOut, Remove, plus gRPC health. **Unit and protocol-streaming tests, race tests and `go vet` pass; an ARM64 Go build succeeds. The ARM64 k3s shell-only milestone passed end-to-end with v0.1.0-alpha.2 (including nonzero exit and cleanup). Pinned JavaScript Actions now execute on ARM64 k3s; the first `pi-wright` verify workload reached native dependency postinstall before a **workspace-volume eviction**, not a confirmed memory OOM. Production use is not recommended.**

## Installation experiment

Build the OCI image for your architecture (`docker buildx build --platform linux/arm64 ...`), substitute its name in [`deploy/example.yaml`](deploy/example.yaml), create `forgejo-jobs` and `forgejo-runner` namespaces, apply [`deploy/plugin-network-policy.yaml`](deploy/plugin-network-policy.yaml) **first** (edit its trusted Runner pod selector), then deploy the example. The example expects the trusted Runner in `forgejo-runner`; if yours is elsewhere, change the manifest namespaces, RoleBinding subject and NetworkPolicy selectors accordingly. Verify the CNI enforces NetworkPolicy and that untrusted job Pods cannot connect to port 50051. Alternatively, co-locate plugin and Runner in one Pod using a UNIX socket (not covered by this example). This is an example, **not** Flux configuration. The plugin requires `rest.InClusterConfig()` and a ServiceAccount; it cannot run outside a cluster without code changes. Its namespace Role needs only `pods` create/get/delete and `pods/exec` create; no cluster-admin, secret access or node socket. Run the Runner where it can reach the plugin Service DNS. Runner config (Runner v13.2.0, default `container.workdir_parent: workspace`):

```yaml
plugins:
  kubernetes:
    address: forgejo-runner-kubernetes.forgejo-runner.svc.cluster.local:50051
runner:
  labels:
    - 'k3s:kubernetes://ubuntu:24.04'
```

Use `runs-on: k3s`, for example:

```yaml
on: push
jobs:
  hello:
    runs-on: k3s
    steps:
      - run: |
          uname -a
          echo 'hello from Kubernetes'
```

A shell-only workflow of this form passed on ARM64 k3s with v0.1.0-alpha.2; this YAML is illustrative, not the exact recorded test. `JOB_NAMESPACE` defaults to `forgejo-jobs`, `JOB_IMAGE` to `ubuntu:24.04`, `JOB_ARCH` to `arm64` (`amd64` for disposable kind tests), `PLUGIN_LISTEN_ADDR` to `0.0.0.0:50051`. Job Pod image selection follows Runner v13.2.0: `jobs.<id>.container.image` becomes `Create.image` and takes precedence; otherwise the `runs-on` plugin label suffix (`Create.label_arg`) supplies the image, falling back to `JOB_IMAGE` only when both are empty. The plugin does not inspect the selected image or supply missing utilities; unsupported images fail to start or exec. Services, per-command user, backend options, capability additions and container actions remain **unsupported**. Runner `container.workdir_parent` must be `workspace`. The job image must contain `/bin/sh`, `/usr/bin/env`, `mkdir`, GNU `tar`, `sleep`, and (for default shell steps) `bash`. Tar archives are streamed by the plugin but extracted/created using `tar` *inside the job image*; this is not independent of image utilities. `ubuntu:24.04` was the shell-only milestone's job image; it lacks the Node 24 interpreter needed to start either pinned JavaScript Action. For JavaScript Actions, select a suitable ordinary multiarch job image in the Runner label or via `jobs.<id>.container.image` (see [actions-integration.md](docs/actions-integration.md)); checkout and setup-node have now executed on ARM64 k3s. The selected image must match the job Pod's ARM64 node selector and contain the required tools; administrators should restrict permitted registries/images with cluster admission policy as appropriate. No host runtime sockets, Podman, kubectl, persistent workspace, registry-based image ENV inspection, or Docker-based Actions. Jobs preserve effective inherited image environment through bounded discovery as documented below. Image building uses an operator-owned remote BuildKit service; no Docker daemon or workflow service containers are supplied.

`Start` waits up to 3 minutes for readiness and diagnoses some unschedulable/image-pull failures. Job Pod has `restartPolicy: Never`, scheduling requests with operator-opt-in resource/storage limits, RuntimeDefault seccomp, `allowPrivilegeEscalation: false`, and **no ServiceAccount token**. The job explicitly remains non-privileged, honoring image USER and ordinary runtime capabilities: no forced UID/GID/non-root or custom capability field (see [job execution](docs/job-security.md)). One disk-backed `emptyDir` is mounted at both `/shared` (runner staging) and `/workspace` (default job working directory): **two paths, one shared storage budget**, removed with the Pod. Container root filesystem is not read-only because `/tmp` and other image paths can be needed. The Runner's requested environment lifetime becomes the Pod active deadline; it is not an automatic TTL deletion. AppArmor is unspecified by default. Operators may set `JOB_APPARMOR_PROFILE=runtime-default`, `unconfined`, or `localhost:<name>` to explicitly select the **job container** AppArmor profile; unset emits no AppArmor field. `unconfined` removes AppArmor confinement only, not seccomp or the other security settings, and should only be used by explicit cluster policy (see [cluster-integration.md](docs/cluster-integration.md#job-apparmor)).

**Alpha.13: no default resource or volume-size limits.** Job requests remain CPU **100m**, memory **128Mi**, ephemeral storage **256Mi**; these are scheduling estimates, not ceilings. `JOB_CPU_LIMIT`, `JOB_MEMORY_LIMIT`, `JOB_EPHEMERAL_STORAGE_LIMIT` and `JOB_WORKSPACE_SIZE_LIMIT` are **omitted unless the operator supplies a positive quantity**. Empty or exact `none` omits a limit; requests use existing defaults when empty and accept `none` to omit. Memory/storage/concurrency policy belongs to the operator or namespace admission, not the executor. Request≤limit is validated only where both exist. Namespace admission/LimitRange can still add defaults or require limits; inspect admitted Pods. Job pull policy remains omitted. See the **[complete Pod-policy inventory, operator contract and acceptance experiment](docs/pod-policy.md)**. Alpha.12 defaults to memory1Gi, ephemeral2Gi and workspace1Gi; alpha.13 removes those defaults. On shared nodes, explicitly choose suitable memory/disk limits, realistic requests and concurrency controls; delegation is not resource protection.

The plugin reads `JOB_WORKSPACE_SIZE_LIMIT` (default **omitted**), `JOB_EPHEMERAL_STORAGE_REQUEST` (default `256Mi`) and `JOB_EPHEMERAL_STORAGE_LIMIT` (default **omitted**) at startup. Supplied values must be **positive Kubernetes byte quantities** (e.g. `5Gi`) or exact `none`. A workspace cap or container limit can be configured independently; if both are supplied, workspace<ephemeral limit leaves room for layers/logs. Requests must not exceed a configured limit. No default capacity policy is imposed. The disk-backed `emptyDir` cap is not a reservation or an addition to the Pod limit; exceeding either budget can cause eviction. Neither guarantee prevents node DiskPressure. The first `pi-wright` verify run exceeded the old 1Gi volume cap during dependency installation; kubelet reported an `emptyDir` eviction, **not** a memory OOM. See [cluster-integration.md](docs/cluster-integration.md#job-storage-budget) for the resource model.

## Image builds

Use an operator-managed persistent BuildKit service with Buildx's **remote**
driver and `--push`. Jobs supply Docker CLI/Buildx and job-scoped registry
credentials. An ordinary workflow environment variable can provide the endpoint;
the plugin needs no builder API or special job class.

The plugin does not provision builders or persistent storage. DinD and its
configuration, sidecar, socket and data volumes are removed. Workflows requiring
`docker run`, Compose or `--load` need a separate execution solution; none is
introduced here. Migrate image publication before upgrading the plugin and drain
active jobs. See [image-building ownership](docs/oci-building-design.md).

The plugin is **trusted infrastructure**: Kubernetes RBAC does not restrict the *contents* of Pods it creates. **There is no gRPC authentication in Runner v13.2's plaintext TCP plugin connection. Without enforced ingress isolation, a job Pod can call the plugin directly and ask it to provision Pods using the plugin's Kubernetes privileges.** Treat the example's ingress NetworkPolicy (or a co-located private UNIX socket) as mandatory, not optional. Isolate the Service from all untrusted workloads and do not expose it outside the trusted cluster. A job Pod receives no Kubernetes API credentials but still has ordinary Pod network access by default, and can access whatever the network allows. Configure NetworkPolicy, namespace quota and other admission controls separately as appropriate. This is Kubernetes container isolation, **not** a VM security boundary. `pods/exec` arguments/environment can be visible to cluster administrators.

**Quiet workflow commands are supported without application heartbeat output.** The plugin configures its gRPC server's client-PING enforcement minimum to **30 seconds**, matching supported Forgejo Runner v13.2.0; `PermitWithoutStream` remains false. This corrects the default five-minute policy that could disconnect quiet active Exec streams. See [Exec liveness research and regression tests](docs/exec-liveness.md). The operator now supplies successful quiet long-running Exec and application smoke evidence; no heartbeat wrapper is recommended.

## Ordinary image-native jobs (alpha.11)

There is **one job model**, not a compatibility/profile system: selected image USER/default identity and runtime capability baseline, with explicit non-privilege/no-new-privileges, RuntimeDefault seccomp, configured AppArmor and existing host/token/network boundaries and operator resource choices. No UID10001 override, job modes, capability list, permission helper or NSS fix. Ordinary workspace writes need no forced group; fsGroup is omitted. Private ephemeral emptyDir roots retain broad 0777 permissions, a within-Pod security characteristic to revisit separately. Start/Exec universally preserve bounded NUL-framed effective image environment, explicit Runner overrides. HOME/PATH and empty values are preserved where they reach the wire; absent HOME gets the writable shared fallback. See the complete [operator contract, capabilities, upgrade behavior and integration handoff](docs/job-security.md).

Local standard-Node diagnostics prove that missing-UID/NSS plus a sanitized child can produce `uv_os_homedir ENOENT`; native registered identities resolve their passwd homes. The specific supplied application failure is **not declared fixed** without separate real integration. [Executor-model research](docs/executor-model.md) records the implemented job-only portion and deferred service design. Services remain rejected; remote image builds do not change that. Alpha.11 publishes that simplified identity default; backward compatibility with the former forced-UID model is not promised. Alpha.12 adds the subsequent resource/pull-policy cleanup. Real-cluster acceptance remains pending.

## Development

Go 1.26+: `go test -race ./...`, `go vet ./...`, `go build ./cmd/forgejo-runner-kubernetes`; `CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build ./cmd/forgejo-runner-kubernetes` for ARM64. GitHub Actions is the bootstrap CI; do not move this project's own CI onto the plugin. Pull requests and manual dispatches validate development; **a pushed `v*` tag runs validation and publishes in one workflow run** (pushing `main` does not launch a duplicate run). Tag CI validates before building/publishing a versioned `linux/amd64` + `linux/arm64` image to GHCR, and publishes binary artifacts, checksums and the **immutable OCI digest** in the GitHub prerelease. Do not use `latest` or deploy a tag when a digest is available. Follow the [migration order](docs/oci-building-design.md) before deploying the no-DinD release. Publication does not establish integration success. The [pinned Actions analysis](docs/actions-integration.md) remains the smaller prior milestone. Keep this repository's own CI on GitHub Actions.

Known gaps: no passing full verification suite. The operator reports that the accepted job Unconfined AppArmor profile removes the explicit child-process `kill EACCES` failure (unchanged verification improves from 142/146 to 143/146). A remaining `uv_os_homedir ENOENT` failure is consistent with the locally proven missing-UID/NSS mechanism, but has not been definitively attributed or fixed. Ordinary image identity/runtime capability/env behavior is documented in [job execution](docs/job-security.md); workflow services remain unsupported. No automated Kubernetes exec transport test (real ARM64 shell and pinned Actions did execute); tar copy is dependent on GNU tar and has not been hardened against malicious archives; no orphan sweeper after plugin crash or API uncertainty, and pod deletion is requested but not watched to completion; only explicit Remove deletes the Pod (a cancelled Kubernetes exec stream may not reliably kill its remote command before Runner removes the environment); startup diagnostics are limited; image env discovery is bounded and universal, not registry metadata inspection; no generalized filesystem helper. Pod identity is deterministic from Runner's per-task name, with labels and an annotation for later orphan tracing. **Do not deploy this to run untrusted public repositories without further security review.** Release, deployment and real-cluster acceptance of the simplified job milestone require separate authorization.
