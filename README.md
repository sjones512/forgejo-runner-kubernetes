# forgejo-runner-kubernetes (experimental)

Proof-of-concept **execution plugin**, not a new CI engine. Licensed under [MIT](LICENSE). Forgejo Runner handles workflows; this gRPC server uses its in-cluster Kubernetes identity to create one ephemeral Pod per job and forward file transfers, stdout/stderr and process exit status through Kubernetes `pods/exec`. **Experimental, not production-ready. Operator-supplied ARM64 integration evidence now covers JavaScript Actions, transfers, quiet Exec, per-job images, native DinD/Buildx build/load and smoke tests, registry publication and registry-backed BuildKit caching. A passing full verification suite has not been demonstrated.**

Target: **Forgejo Runner v13.2.0** (`plugin.v1alpha`, commit `df6b843fb929bb04b933b09c6bf208774d42480b`). See [research / protocol mapping / tradeoffs](docs/research.md) and the [cluster integration contract](docs/cluster-integration.md). Protocol is alpha and may change without notice. Implemented RPCs: Capabilities, Create, Start, Exec, CopyIn, CopyOut, Remove, plus gRPC health. **Unit and protocol-streaming tests, race tests and `go vet` pass; an ARM64 Go build succeeds. The ARM64 k3s shell-only milestone passed end-to-end with v0.1.0-alpha.2 (including nonzero exit and cleanup). Pinned JavaScript Actions now execute on ARM64 k3s; the first `pi-wright` verify workload reached native dependency postinstall before a **workspace-volume eviction**, not a confirmed memory OOM. Production use is not recommended.**

## Installation experiment

Build the OCI image for your architecture (`docker buildx build --platform linux/arm64 ...`), substitute its name in [`deploy/example.yaml`](deploy/example.yaml), create `forgejo-jobs` and `forgejo-runner` namespaces, apply [`deploy/plugin-network-policy.yaml`](deploy/plugin-network-policy.yaml) **first** (edit its trusted Runner pod selector), then deploy the example. The example expects the trusted Runner in `forgejo-runner`; if yours is elsewhere, change the manifest namespaces, RoleBinding subject and NetworkPolicy selectors accordingly. Verify the CNI enforces NetworkPolicy and that untrusted job Pods cannot connect to port 50051. Alternatively, co-locate plugin and Runner in one Pod using a UNIX socket (not covered by this example). This is an example, **not** Flux configuration. The plugin requires `rest.InClusterConfig()` and a ServiceAccount; it cannot run outside a cluster without code changes. Its namespace Role needs only `pods` create/get/delete and `pods/exec` create; no cluster-admin, secret access or node socket. Run the Runner where it can reach the plugin Service DNS. Runner config (Runner v13.2.0, default `container.workdir_parent: workspace`):

```yaml
plugins:
  kubernetes:
    address: forgejo-runner-kubernetes.forgejo-runner.svc.cluster.local:50051
runner:
  labels:
    - 'k3s:kubernetes://ubuntu:24.04'
```

Use `runs-on: k3s`, for example:

```yaml
on: push
jobs:
  hello:
    runs-on: k3s
    steps:
      - run: |
          uname -a
          echo 'hello from Kubernetes'
```

A shell-only workflow of this form passed on ARM64 k3s with v0.1.0-alpha.2; this YAML is illustrative, not the exact recorded test. `JOB_NAMESPACE` defaults to `forgejo-jobs`, `JOB_IMAGE` to `ubuntu:24.04`, `JOB_ARCH` to `arm64` (`amd64` for disposable kind tests), `PLUGIN_LISTEN_ADDR` to `0.0.0.0:50051`. Job Pod image selection follows Runner v13.2.0: `jobs.<id>.container.image` becomes `Create.image` and takes precedence; otherwise the `runs-on` plugin label suffix (`Create.label_arg`) supplies the image, falling back to `JOB_IMAGE` only when both are empty. The plugin does not inspect the selected image or supply missing utilities; unsupported images fail to start or exec. Services, per-command user, backend options, capability additions and container actions remain **unsupported**. Runner `container.workdir_parent` must be `workspace`. The job image must contain `/bin/sh`, `/usr/bin/env`, `mkdir`, GNU `tar`, `sleep`, and (for default shell steps) `bash`. Tar archives are streamed by the plugin but extracted/created using `tar` *inside the job image*; this is not independent of image utilities. `ubuntu:24.04` was the shell-only milestone's job image; it lacks the Node 24 interpreter needed to start either pinned JavaScript Action. For JavaScript Actions, select a suitable ordinary multiarch job image in the Runner label or via `jobs.<id>.container.image` (see [actions-integration.md](docs/actions-integration.md)); checkout and setup-node have now executed on ARM64 k3s. The selected image must match the job Pod's ARM64 node selector and contain the required tools; administrators should restrict permitted registries/images with cluster admission policy as appropriate. No host runtime sockets, Podman, kubectl, persistent workspace, registry-based image ENV inspection, or Docker-based Actions. Jobs preserve effective inherited image environment through bounded discovery as documented below. A fixed **operator-opt-in privileged DinD sidecar** is now available for ordinary shell steps using Docker CLI; generic workflow service containers remain unsupported.

`Start` waits up to 3 minutes for readiness and diagnoses some unschedulable/image-pull failures. Job Pod has `restartPolicy: Never`, operator CPU/memory requests and limits plus bounded ephemeral storage, RuntimeDefault seccomp, `allowPrivilegeEscalation: false`, and **no ServiceAccount token**. The job explicitly remains non-privileged, honoring image USER and ordinary runtime capabilities: no forced UID/GID/non-root or custom capability field (see [job execution](docs/job-security.md)). One disk-backed `emptyDir` is mounted at both `/shared` (runner staging) and `/workspace` (default job working directory): **two paths, one shared storage budget**, removed with the Pod. Container root filesystem is not read-only because `/tmp` and other image paths can be needed. The Runner's requested environment lifetime becomes the Pod active deadline; it is not an automatic TTL deletion. AppArmor is unspecified by default. Operators may set `JOB_APPARMOR_PROFILE=runtime-default`, `unconfined`, or `localhost:<name>` to explicitly select the **job container** AppArmor profile; unset emits no AppArmor field. `unconfined` removes AppArmor confinement only, not seccomp or the other security settings, and should only be used by explicit cluster policy (see [cluster-integration.md](docs/cluster-integration.md#job-apparmor)).

**Alpha.12 policy cleanup after alpha.11:** ordinary jobs default to CPU request **100m with no CPU limit**, memory request/limit **128Mi/1Gi**. Four operator settings—`JOB_CPU_REQUEST`, `JOB_CPU_LIMIT`, `JOB_MEMORY_REQUEST`, `JOB_MEMORY_LIMIT`—choose positive Kubernetes quantities; exact `none` omits a field (empty selects its default). Requests guide scheduling, not ceilings; CPU limits throttle, memory limits can OOM-kill. Request≤limit is validated where both exist. Namespace admission/LimitRange can add defaults or require limits. Job pull policy is now omitted so Kubernetes handles latest/untagged images normally. Fixed DinD budgets are separate and unchanged. See the **[complete Pod-policy inventory, operator contract and CPU acceptance experiment](docs/pod-policy.md)**. Alpha.11 hard-caps the job at1CPU; alpha.12 removes that default.

The plugin reads `JOB_WORKSPACE_SIZE_LIMIT` (default `1Gi`), `JOB_EPHEMERAL_STORAGE_REQUEST` (default `256Mi`) and `JOB_EPHEMERAL_STORAGE_LIMIT` (default `2Gi`) at startup and applies them to each generated job Pod. Values must be **positive Kubernetes byte quantities** (e.g. `5Gi`); the storage request must not exceed its limit, and the workspace cap must be **strictly below** the overall ephemeral-storage limit to leave room for writable container layers and logs. If increasing the workspace cap, configure the limit coherently (for example, `JOB_WORKSPACE_SIZE_LIMIT=5Gi` with an appropriately larger `JOB_EPHEMERAL_STORAGE_LIMIT`, and set the request to a realistic scheduling estimate). The disk-backed `emptyDir` cap is not a reservation or an addition to the Pod limit; exceeding either budget can cause eviction. Neither guarantee prevents node DiskPressure. The first `pi-wright` verify run exceeded the old 1Gi volume cap during dependency installation; kubelet reported an `emptyDir` eviction, **not** a memory OOM. See [cluster-integration.md](docs/cluster-integration.md#job-storage-budget) for the resource model.

## Optional job-local Docker

`JOB_DIND_ENABLED=true` adds one fixed rootful **privileged** Docker daemon sidecar to every generated Pod; default is **false**, preserving the existing single-container environment. Enabling requires `JOB_DIND_IMAGE` pinned by `@sha256:…` and a job namespace that admits Privileged PSA. The image must support ARM64 (`JOB_ARCH`), rootful DinD and the fixed Unix-only daemon arguments. There is no mutable default image and no workflow-controlled privilege or new execution class.

DinD does not change the job's ordinary image identity, security settings or image selection. It receives `DOCKER_HOST=unix:///run/forgejo-docker/docker.sock` through a dedicated shared socket `emptyDir`, plus `TMPDIR=/shared/tmp` for daemon-visible bind fixtures. Both containers mount the same workspace at `/shared` and `/workspace`; private `/tmp` is **not** shared. Publishing jobs must supply their own compatible Docker CLI/buildx; the plugin installs no tools. `Start` waits for the sidecar's bounded `docker info` readiness probe as well as job readiness before workflow execution. One Runner `Remove` deletes both containers and their storage.

Daemon data at the fixed `/var/lib/docker` root is a separately bounded disk `emptyDir` (default **10Gi**, daemon ephemeral limit **12Gi**, request **1Gi**), mounted at that **exact** path to override the official image's `VOLUME /var/lib/docker`. Alpha.8's parent `/var/lib` mount was shadowed. Daemon CPU/memory requests default to **100m/128Mi**, limits **2 CPU/2Gi**. These and the storage driver are operator configurable. Docker build layers/test volumes can require substantially larger budgets; requests are not measured idle usage, and privileged nested cgroup accounting must be integration-verified. See the complete [configuration/security/storage contract](docs/cluster-integration.md#job-local-docker) and [approved design](docs/oci-building-design.md).

**This exposes a per-job daemon, not the node Docker/containerd socket.** No hostPath, host PID/network or job Kubernetes token is added. Nevertheless, controlling privileged DinD gives repository code an elevated nested runtime and greater kernel/device/mount attack surface, including verification jobs that never use Docker. Only opt in for trusted-repository CI. Job AppArmor/seccomp remain separate and unchanged; the daemon alone explicitly uses Unconfined seccomp/AppArmor. **The operator reported successful alpha.8 ARM64 DinD readiness/builds/isolation/cleanup but a failed data-volume acceptance; alpha.9 corrected the exact mount. Later supplied integration evidence establishes corrected storage accounting/cleanup, native application builds/smokes, publication and registry-backed caching.** These are separate-agent observations, not measurements repeated by this repository task.

The plugin is **trusted infrastructure**: Kubernetes RBAC does not restrict the *contents* of Pods it creates. **There is no gRPC authentication in Runner v13.2's plaintext TCP plugin connection. Without enforced ingress isolation, a job Pod can call the plugin directly and ask it to provision Pods using the plugin's Kubernetes privileges.** Treat the example's ingress NetworkPolicy (or a co-located private UNIX socket) as mandatory, not optional. Isolate the Service from all untrusted workloads and do not expose it outside the trusted cluster. A job Pod receives no Kubernetes API credentials but still has ordinary Pod network access by default, and can access whatever the network allows. Configure NetworkPolicy, namespace quota and other admission controls separately as appropriate. This is Kubernetes container isolation, **not** a VM security boundary. `pods/exec` arguments/environment can be visible to cluster administrators.

**Quiet workflow commands are supported without application heartbeat output.** The plugin configures its gRPC server's client-PING enforcement minimum to **30 seconds**, matching supported Forgejo Runner v13.2.0; `PermitWithoutStream` remains false. This corrects the default five-minute policy that could disconnect quiet active Exec streams. See [Exec liveness research and regression tests](docs/exec-liveness.md). The operator now supplies successful quiet long-running Exec and application smoke evidence; no heartbeat wrapper is recommended.

## Ordinary image-native jobs (alpha.11)

There is **one job model**, not a compatibility/profile system: selected image USER/default identity and runtime capability baseline, with explicit non-privilege/no-new-privileges, RuntimeDefault seccomp, configured AppArmor and existing host/token/resource/network boundaries. No UID10001 override, job modes, capability list, permission helper or NSS fix. fsGroup10001 is set **only for fixed-DinD socket access**; ordinary workspace writes need no forced group. Private ephemeral emptyDir roots retain broad 0777 permissions (potentially 02777 with fsGroup), a within-Pod security characteristic to revisit separately. Start/Exec universally preserve bounded NUL-framed effective image environment, stored daemon defaults and explicit Runner overrides. HOME/PATH and empty values are preserved where they reach the wire; absent HOME gets the writable shared fallback. See the complete [operator contract, capabilities, upgrade behavior and integration handoff](docs/job-security.md).

Local standard-Node diagnostics prove that missing-UID/NSS plus a sanitized child can produce `uv_os_homedir ENOENT`; native registered identities resolve their passwd homes. The specific supplied application failure is **not declared fixed** without separate real integration. [Executor-model research](docs/executor-model.md) records the implemented job-only portion and deferred service design. Services remain rejected and fixed DinD remains intact. Alpha.11 publishes that simplified identity default; backward compatibility with the former forced-UID model is not promised. Alpha.12 adds the subsequent resource/pull-policy cleanup. Real-cluster acceptance remains pending.

## Development

Go 1.26+: `go test -race ./...`, `go vet ./...`, `go build ./cmd/forgejo-runner-kubernetes`; `CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build ./cmd/forgejo-runner-kubernetes` for ARM64. GitHub Actions is the bootstrap CI; do not move this project's own CI onto the plugin. Pull requests and manual dispatches validate development; **a pushed `v*` tag runs validation and publishes in one workflow run** (pushing `main` does not launch a duplicate run). Tag CI validates before building/publishing a versioned `linux/amd64` + `linux/arm64` image to GHCR, and publishes binary artifacts, checksums and the **immutable OCI digest** in the GitHub prerelease. Do not use `latest` or deploy a tag when a digest is available. Current next milestone: separately authorized real-cluster [CPU/resource acceptance](docs/pod-policy.md#breaking-changes-and-separate-acceptance) for alpha.12. Publication does not establish integration success. The [pinned Actions analysis](docs/actions-integration.md) remains the smaller prior milestone. Keep this repository's own CI on GitHub Actions.

Known gaps: no passing full verification suite. The operator reports that the accepted job Unconfined AppArmor profile removes the explicit child-process `kill EACCES` failure (unchanged verification improves from 142/146 to 143/146). A remaining `uv_os_homedir ENOENT` failure is consistent with the locally proven missing-UID/NSS mechanism, but has not been definitively attributed or fixed. Ordinary image identity/runtime capability/env behavior is documented in [job execution](docs/job-security.md); workflow services remain unsupported. No automated Kubernetes exec transport test (real ARM64 shell and pinned Actions did execute); tar copy is dependent on GNU tar and has not been hardened against malicious archives; no orphan sweeper after plugin crash or API uncertainty, and pod deletion is requested but not watched to completion; only explicit Remove deletes the Pod (a cancelled Kubernetes exec stream may not reliably kill its remote command before Runner removes the environment); startup diagnostics are limited; image env discovery is bounded and universal, not registry metadata inspection; no generalized filesystem helper. Pod identity is deterministic from Runner's per-task name, with labels and an annotation for later orphan tracing. **Do not deploy this to run untrusted public repositories without further security review.** Release, deployment and real-cluster acceptance of the simplified job milestone require separate authorization.
